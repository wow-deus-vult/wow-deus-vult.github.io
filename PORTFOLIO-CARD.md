# Deus Vult Guild Stats — сайт статистики WoW-гільдії

**Суть:** гільдія бачить на одному сайті бойові рейтинги всіх гравців і спорядження кожного персонажа «як у грі» — дані збираються й публікуються самі, щодня.
**Замовник:** гільдія Deus Vult на приватному WoW-сервері Freedom x5 (автор — учасник гільдії).
**Запущено:** 06.2026 (перший коміт 26.06.2026).
**Стан:** у бою — сайт живий, автооновлення працює щодня (останній автокоміт 03.08.2026).

## Цифри

- **267 комітів** за перші ~6 тижнів — основна розробка 26.06–13.07, далі щоденні автооновлення (джерело: git log)
- **28 Python-скриптів, ~7 000 рядків** — 7 збирачів рейтингів + конвеєр арморі з 4 кроків (джерело: код)
- **10 розділів сайту** — рейтинги DPS/хіл/танк, статистика зіль, сумарний урон, аналітика, арморі та ін. (джерело: структура репозиторію)
- **3 935 персонажів** у арморі, з них **832 з повними даними** (геми, чарки, таланти); **6 234 предметів** у кеші (джерело: armory_data.json, стан на 08.2026)
- **358 гравців** у DPS-рейтингу (джерело: data/guild-data.json)
- **2 незалежні контури автооновлення**: Windows Task Scheduler о 10:00 на ПК автора + GitHub Actions о 4:00 UTC (джерело: update_guild_data.bat, .github/workflows/update-data.yml)
- **1 935 предметів** мали на сервері інші характеристики, ніж у публічній базі wowhead — виправлено власним парсером клієнтського кешу (джерело: вивід merge_wdb_items.py у git-історії)
- не виміряно: відвідуваність сайту й економія часу — аналітики відвідувань у коді немає

## Про що це

Гільдія грає на приватному сервері World of Warcraft, у якого немає офіційної «оружейної палати» і рейтингів: дані про бої лежать на сторонньому сайті логів, а спорядження гравців видно лише всередині гри. Порівняти гравців або перевірити, хто як одягнений, можна було тільки вручну.

Проєкт закриває це одним сайтом. Щодня скрипти збирають бойові логи зі стороннього сервісу, а внутрішньоігрові дані — прямо з файлів WoW-клієнта: спеціально доопрацьований ігровий аддон непомітно «фотографує» спорядження кожного гравця, на якого наведено курсор у грі, включно з талантами та окремими комплектами під різні ролі (бойовий/танковий). Сайт показує це як ігрова панель персонажа: характеристики збігаються з грою один в один — це звірено на живому персонажі по кожному числу.

Особливість сервера в тому, що адміністрація змінює характеристики предметів, тож публічні бази даних (wowhead) часто брешуть. Для цього побудований окремий шар «серверної правди»: парсер бінарного кешу ігрового клієнта, який читає характеристики предметів саме такими, якими їх надіслав сервер.

Оновлення повністю автоматичне: вранці планувальник запускає збирачів, результат комітиться в Git і публікується на GitHub Pages, а в Discord автору приходить звіт — скільки гравців оновлено, скільки нових. Окремий сторож о 12:00 перевіряє, що регламент відпрацював, і пише в Discord, якщо ні.

## Як це зроблено

- **Технології:** Python 3 (requests, mpyq — читання ігрових MPQ-архівів), фронтенд — статичний HTML + ванільний JavaScript без фреймворків, Lua-патчі до ігрового аддона GearScore.
- **Дані:** без СУБД — JSON-файли в репозиторії (21 файл рейтингів + кеші арморі); історія змін = git-історія.
- **Джерела даних:** uwu-logs.xyz (API + HTML), wowhead (tooltip-API), файли WoW-клієнта (SavedVariables Lua, itemcache.wdb, DBC-таблиці з MPQ-архівів — назви гемів/чарок/талантів двома мовами, ігрові формули крита).
- **Інтеграції:** Discord Bot API (щоденні звіти в особисті повідомлення), Google Sheets (сторінка-пасхалка).
- **Розгортання:** GitHub Pages; оновлення — локальний Task Scheduler (повний цикл, бо потребує файлів гри) + GitHub Actions (частина збирачів, що працюють лише з вебджерел); перед пушем — валідація всіх JSON.

## Що було найскладнішим

- **Сервер змінює предмети, а публічні бази про це не знають.** Написаний парсер бінарного кешу клієнта (формат відповіді сервера на запит предмета): характеристики, броня, сокети читаються такими, якими їх бачить гра. Виявилось, що майже 2 000 предметів відрізнялись від wowhead.
- **Характеристики персонажа «один в один як у грі» без доступу до серверної БД.** Розрахунок складається з базових статів раси/класу (таблиці відкритого серверного ядра), спорядження, гемів, чарок, бонусів сокетів і талантів. Формули крита взяті з ігрових таблиць у клієнті, бонуси талантів — з аур заклинань, а не з довідників. Калібрування йшло по живому персонажу до повного збігу: розбіжність у 15 одиниць крита в результаті звелась до скороченого запису назви чарки в ігровій базі.
- **Збір чужого спорядження без жодного втручання на сервері.** Ігровий аддон доопрацьований так, що наведення курсора на гравця тихо зчитує його таланти і зберігає знімок спорядження окремо для кожної ролі. Дані про той самий предмет чи гравця приходять з різною якістю — тому є багаторівневий захист: знімок нижчої якості (наприклад, «трансмог»-вигляд замість реального шмоту) не може затерти повноцінний.
- **Стійкість щоденного конвеєра.** Зовнішній сервіс логів обмежує частоту запитів — збирачі мають черги відкладених логів і карту дублікатів, щоб один і той самий бій не порахувався двічі різними збирачами.

## Як росла майстерність

Це найбільший видимий репозиторій автора, порівняти з попередніми проєктами в хронології немає з чого — тож лише спостереження всередині нього. Секрети винесені в `.env` і закриті `.gitignore` з самого початку; спільна логіка збирачів одразу виділена в модулі (парсер складу гільдії, черга логів, дедуплікація) замість копіювання між сімома скриптами. Перед автоматичним пушем стоїть валідація JSON, яка блокує публікацію битих даних, а окремий сторож стежить, чи відпрацював ранковий регламент. Повідомлення комітів здебільшого пояснюють причину зміни, а не лише дію (наприклад, чому парсер губив перший елемент Lua-масиву). Автоматичних тестів у репозиторії немає — перевірки виконуються калібруванням на живих даних.
